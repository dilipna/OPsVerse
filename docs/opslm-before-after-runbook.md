## 1. What the comparison actually has to be

**The valid comparison is `Qwen3-4B-Base` vs `OpsLM-v1`, both served through the same
harness.** Not OpsLM vs Gemini.

The existing `rag-quality-smoke` baseline was generated by **Gemini 3.5 Flash**, a far
larger and stronger model. OpsLM will almost certainly score worse than it, and that would
tell you *nothing* about whether fine-tuning worked — only that a 4B model is smaller than
Gemini. Quoting that as a "before/after" would be a genuine methodological error, and the
kind a panel catches.

So this needs **two serves**: base, then fine-tune. Budget accordingly.

**Realistic time:** ~45-70 min for the first serve (install + load + tunnel), ~15 min for
the second (same runtime, swap the model), ~10 min per eval run. **Total 1.5-2.5 h if
nothing fights you.** Three prior Colab sessions were burned on GPU work — plan for it to
fight you.

## 3. THE LANDMINE — read before running any eval

`opsverse_evals.rag_suite` writes to a **fixed filename** regardless of which model
generated the answers:

- `docs/reports/rag-quality-smoke-summary.json`, with `"report": "rag-quality-smoke"`

And `opsverse_evals.regression` pins **three thresholds** against that exact report:
`judge:faithfulness >= 0.9`, `judge:answer_relevance >= 0.85`, `judge:citation_used >= 0.9`.

**If you run the eval with default `--out`, you will:**
1. overwrite the committed Gemini baseline,
2. very likely fail the regression gate (a 534-example 4B fine-tune will not hit 0.9
   faithfulness), and
3. break demo step 3, which is *"15/15, all green"* — on stage.

**Always write to a scratch directory. Never the default.**

```powershell
mkdir docs\reports\opslm-eval -Force        # scratch; regression never reads it
```

`regression` only reads `--reports docs/reports` (non-recursive), so a subdirectory is safe.

## 4. Serve the model (Colab — you drive the UI)

Use **`benchmarks/notebooks/opslm_inference_bench_colab.ipynb`**. It already contains the
hardened install recipe; do not improvise a new one.

The gotchas it encodes (from three burned sessions — do not rediscover):

1. `uv pip install --system vllm --torch-backend=auto` → **restart the runtime** → set
   `LD_LIBRARY_PATH` and ctypes-preload `libcudart.so.13`.
2. **AWQ is dropped.** AutoAWQ is unmaintained past torch 2.6. Do not retry it.
3. **Stop vLLM before starting Ollama** or Ollama silently runs ~80% on CPU. Verify with
   `ollama ps` showing 100% GPU. (Not needed here — this procedure uses vLLM only.)
4. **Colab recycles the whole runtime.** Print every result to stdout the moment you have
   it, and copy it out immediately.

**Serve run A — the base model:**

```bash
vllm serve unsloth/Qwen3-4B-Base --port 8000 --max-model-len 4096 --gpu-memory-utilization 0.90
```

**Expose it.** Any OpenAI-compatible reachable URL works (cloudflared / ngrok). Copy the
public base URL; you want the form `https://<host>/v1`.

**Smoke-test the tunnel from your laptop before going further** — this is the step that
silently wastes the most time:

```powershell
curl.exe -s https://<tunnel-host>/v1/models
```

If that doesn't return JSON listing the model, **stop and fix the tunnel.** Do not proceed.

## 5. Point the platform at it — RESTART the API

> ⚠️ **The env vars go on the API server, not on the eval command.** `rag_suite` is just an
> HTTP client for `http://localhost:8100/v1/chat`; prefixing variables onto *it* changes
> nothing. The handoff's one-liner had this wrong.
>
> ⚠️ The setting is **`OPSVERSE_CHAT_API_BASE`** (from `chat_api_base` in
> `libs/core/src/opsverse_core/settings.py`). There is no `OPSVERSE_LLM_API_BASE`.

Stop the running uvicorn, then in that terminal:

```powershell
$env:OPSVERSE_CHAT_MODEL    = 'openai/Qwen3-4B-Base'      # litellm openai/ prefix = OpenAI-compatible server
$env:OPSVERSE_CHAT_API_BASE = 'https://<tunnel-host>/v1'
$env:OPSVERSE_LANGFUSE_HOST = 'http://localhost:3002'
uv run uvicorn opsverse_api.main:app --port 8100
```

Confirm the platform is really talking to the tunnel before spending an eval on it:

```powershell
$body = '{"query":"What is a Kubernetes readiness probe?","stream":false}'
$r = Invoke-RestMethod -Uri http://localhost:8100/v1/chat -Method Post -ContentType 'application/json' -Body $body
$r.done.model      # MUST show your model, not gemini/*
```

**If that prints `gemini/...`, the override did not take — stop and fix it.** Everything
downstream would be measuring the wrong model.

## 6. Run the evals — scratch output only

```powershell
# BASE model
uv run python -m opsverse_evals.rag_suite --n 20 --out docs/reports/opslm-eval --run-id base-qwen3-4b
Rename-Item docs\reports\opslm-eval\rag-quality-smoke-summary.json base-qwen3-4b.json
```

Then **swap the served model to OpsLM** (Colab: stop vLLM, `vllm serve dhf1234/OpsLM-v1
--port 8000 ...`), update `OPSVERSE_CHAT_MODEL` to `openai/OpsLM-v1`, **restart uvicorn
again**, re-confirm `$r.done.model`, and:

```powershell
uv run python -m opsverse_evals.rag_suite --n 20 --out docs/reports/opslm-eval --run-id opslm-v1
Rename-Item docs\reports\opslm-eval\rag-quality-smoke-summary.json opslm-v1.json
```

**Rename immediately after each run** — the second run overwrites the first otherwise.

**Quota note:** generation goes to your served model (no Gemini quota). Judging uses
`eval_generator_model` = `gemini-3.1-flash-lite`, which has a large separate quota. **This
procedure does not touch the 20/day `3.5-flash` limit** — so your live-chat demo step is
unaffected.

## 7. Interpreting it honestly — including if the fine-tune lost

n=20 with an LLM judge is a **smoke test, not a proof**. Report it as a direction, with the
n attached, exactly as `capacity-and-slo-v1.md` does.

**If OpsLM > base:** you have closed the gap. Say *"fine-tuning improved faithfulness from
X to Y on a 20-case grounded set — small n, directional, and the harness predates the
model."*

**If OpsLM ≈ base (most likely):** this is still a result, and an honest one.
> "No measurable difference at n=20 on 534 training examples. That's the expected outcome
> for a dataset that small, and I'd rather report it than not run it. It tells me the next
> move is data volume, not another training run."

**If OpsLM < base:** report it. A negative result you ran and published is a *stronger*
signal than an untested claim — and you already have the perfect frame, because your eval
harness has falsified you twice before.

Whatever the outcome, **do not overwrite** `docs/reports/rag-quality-smoke-summary.json`.
Write a new file, e.g. `docs/reports/opslm-before-after-v1.md`, and update
`registry/models.json` `eval.before_after_vs_base` from `"pending"` to the finding, then
regenerate: `uv run python registry/registry.py --out docs/model-registry.md`.
